# Query 构造

这一步决定拿哪段文字去检索。输入是一轮对话，输出是一段字符串。这段字符串交给 MiniLM 编成向量，再到 FAISS 里找文档。实现在 `src/query.py` 的 `build_query`，由 `scripts/run_baseline.py` 对每一轮调用。

检索器不记得前面说过什么。它只把这段字符串变成向量，去和文档比。多轮对话里，用户后面说的话经常把已经说过的内容省掉。三种模式是三种拿法，用 `--query_mode` 选一种，不是三条同时跑的流程。

比如第一轮是「遗属津贴要多少社保积分」，第二轮只说「那孩子呢」。

- `question`：检索词只有「那孩子呢」。这是现在的默认，也是基线。
- `history`：把前面几句一起拿去检索，「遗属」「积分」这些词还在。
- `rewrite`：用一句已经补全的问句，例如「孩子领取遗属津贴要多少积分」。

`history` 和 `rewrite` 是后面改进 Query 构造时要改的两处。现在 `history` 只是把最近几句接在一起，`rewrite` 只是读 QReCC 里已经写好的句子，没有自己的改写。

## 一轮里能用的三样文字

三种模式都只从这一轮已经有的文字里挑。

| 字段 | 含义 |
|---|---|
| `question` | 当前这一轮用户说的话 |
| `history` | 这一轮之前的发言，每条是 `(角色, 文本)`，角色是 `user` 或 `agent`。不含当前这句 |
| `rewrite` | 数据里已经写好的完整问句。只有 QReCC 有，来自 `Truth_rewrite`。另外两个数据集是空的 |

三个数据集的列名不同，读进 `src/schema.py` 的 `Example` 之后都是这三样：

| 数据集 | `question` 从哪来 | `history` 从哪来 |
|---|---|---|
| MultiDoc2Dial | 当前 user 轮的 `utterance` | 同一段对话里更早的 user / agent 发言 |
| QReCC | `Question` | `Context`，按顺序交替当成 user、agent |
| TopiOCQA | `Question` | `Context`，按顺序交替当成 user、agent |

## 三种拼法

不写 `--query_mode` 时用 `question`。

### question

只返回 `question`。

### history

一个样本是用户的一轮，不是整段对话。当前这句话放在 `question`，这一轮之前的发言放在 `history`，当前这句不在里面。`history` 模式把前面这些发言接上，再在最后加上当前这句。

QReCC 读到第三轮时，原始数据是这样分开的：

```text
Context[0]  What is a physician's assistant?
Context[1]  physician assistants are medical providers ...
Context[2]  What are the educational requirements required to become a physician's assistant?
Context[3]  Complete your bachelor's degree ...
Question    What does it cost?
```

`Context` 是一个字符串列表，没有角色字段。偶数条当作前面用户问过的话，奇数条当作系统当时的回答。当前这句 `What does it cost?` 不在 `Context` 里。拼出来是：

```text
User: What is a physician's assistant?
Agent: physician assistants are medical providers ...
User: What are the educational requirements required to become a physician's assistant?
Agent: Complete your bachelor's degree ...
User: What does it cost?
```

只拿 `Question` 去检索，检索词是 “What does it cost?”，看不出问的是医师助理的花费。接上前面几句之后，physician's assistant 还在这段文字里。TopiOCQA 的 `Context` 和 `Question` 也是这个排法。

MultiDoc2Dial 不叫 `Context`。一段对话是 `turns` 数组，每一句自己带 `role: user` 或 `agent`。程序顺着数组往下走，遇到用户的一句，就把更早的 `turns` 当作 `history`，当前这句当作 `question`。

默认最多带前面 6 条发言（`--max_history_turns`）。用户一句、系统一句各算一条，所以大约是三轮问答，不是六轮。当前问题总是加在最后，不占这 6 条的名额。对话第一句前面没有内容，这时拼出来就只有当前这句，前面不加 `User:`。

### rewrite

`rewrite` 用的是数据里另外写好的一列，不是把 `Context` 再拼一遍。只有 QReCC 有这一列，字段名是 `Truth_rewrite`。`src/data/qrecc.py` 把它读进 `example.rewrite`。这一列有内容时，检索文本就是这一句，`Context` 和 `Question` 都不再接进去。

还是上面那一轮。原始数据里当前问题和改写句是分开的两列：

```text
Question        What does it cost?
Truth_rewrite   What does it cost to become a physician's assistant?
```

`Question` 沿用了前面的话题，自己看不懂问的是什么花费。`Truth_rewrite` 是数据集提供的改写，把「医师助理」补进这一句。`rewrite` 模式拿去检索的只有第二句。程序没有生成这句，只是把这列原样读出来。

MultiDoc2Dial 和 TopiOCQA 没有 `Truth_rewrite` 这种列，`example.rewrite` 是空的。这时 `rewrite` 模式退回上面的 `history` 拼法。

## 改进时改哪里

检索用的那段文字只在 `src/query.py` 的 `build_query` 里拼好。`scripts/run_baseline.py` 调用它，再把返回值交给 `store.search`。

只想对比现在的三种拿法，不用改代码。`--query_mode` 分别用 `question`、`history`、`rewrite` 跑，结果在 `results/<dataset>_<split>_<query_mode>_k<top_k>.jsonl`。

要改拼法，就改 `build_query` 里对应的分支：

| 改什么 | 改哪里 |
|---|---|
| 基线，只用当前这句 | `question` 分支，现在是 `return example.question` |
| 历史怎么接、带几句 | `history` 分支。它调用 `example.history_text`，再把当前问题接在最后。行首的 `User:` / `Agent:` 在 `src/schema.py` 的 `history_text` |
| 自己的改写 | `rewrite` 分支。现在这里有 `example.rewrite` 就直接返回，否则改走 `history`。新的改写函数放到例如 `src/rewrite.py`，由这个分支调用 |

QReCC 的金标改写由 `src/data/qrecc.py` 从 `Truth_rewrite` 读进 `example.rewrite`。这列留着和自己的改写对照。`src/data/` 下三个文件只负责把原始列填进 `Example`。

再加一种拿法时，把名字写进同文件的 `QUERY_MODES`，并在 `build_query` 里加一个分支。`run_baseline.py` 的 `--query_mode` 用的就是这个元组。

交给 Qwen 的文字是另一次调用：`run_baseline.py` 里的 `generator.generate(...)`，传入的是原来的 `example.question` 和 `example.history_text`。改写句也要交给生成时，改的是这一次调用。
