# Top-K 检索

Query 构造得到一段字符串之后，用这段字符串去已经建好的索引里找出最像的 K 块文档。实现在 `src/index.py` 的 `FaissStore.search`。`scripts/run_baseline.py` 对每一轮调用它，默认 `--top_k 5`。

这一步不重新读原始语料，也不重新切块。它打开 `data/indices/<dataset>/` 里已有的三个文件：`index.faiss` 是向量，`passages.jsonl` 是对应的原文，`meta.json` 里记着建索引时用的模型。查询用的也是这个模型，本机路径是 `models/all-MiniLM-L6-v2`。索引怎么生成见 [../文档预处理与索引构建/索引.md](../文档预处理与索引构建/索引.md)。

## 一次检索做什么

1. 把查询字符串交给 MiniLM，得到一个 384 维向量，再除以它自己的长度，使长度为 1。这和建索引时对文档块的做法相同，所以两边能比。
2. 用这个向量和索引里的每一条做内积。两边长度都是 1，内积就是余弦相似度，大约在 -1 到 1，越大越像。
3. 取得分最高的 K 条。`IndexFlatIP` 会和全部向量都算一遍，按分数从高到低返回。返回的编号就是 `passages.jsonl` 的行号，用这个行号取出原文。

索引里的块数少于 K 时，FAISS 会用 -1 把空位补满。这些 -1 会被丢掉，所以实际返回的条数可以少于 K。

当前索引进去的范围：MultiDoc2Dial 是全部文档；QReCC 和 TopiOCQA 是按文件名排序后的前 20000 条 passage，切块之后分别大约 7.6 万和 2.7 万块。具体块数在各自的 `meta.json` 的 `num_chunks`。全量语料没有全部编进后两个索引，检索只能在已经编进去的块里找。

## 检索结果写到哪里

`run_baseline.py` 把每一轮写进 `results/<dataset>_<split>_<query_mode>_k<top_k>.jsonl`。文件是换行展开的 JSON 数组，每一项是一轮。和检索直接相关的字段：

| 字段 | 内容 |
|---|---|
| `query` | 实际拿去编码的那段字符串 |
| `retrieved` | K 条命中。每条有 `pid`、`source_id`、`score`、`is_gold`、`title`，以及正文的前 300 个字符 |
| `gold_passage_ids` | 这一轮标注的标准段落编号。检索时不用它过滤结果 |

交给后面生成的是这 K 块的完整正文，不是截过的 300 字。分数和 `is_gold` 只写进结果文件，不传给生成。

`is_gold` 表示这一条是不是标注的那一块，由 `src/matching.py` 的 `hit_is_gold` 计算。MultiDoc2Dial 直接比切块号 `doc_id#k`。QReCC 比 `#` 前面的段落编号。TopiOCQA 的维基页面号不在检索语料里，改用金标正文：命中文本能在 `Gold_passage.text` 里找到才算。细节见 [../文档预处理与索引构建/数据集.md](../文档预处理与索引构建/数据集.md) 的「加载时留下了什么」。

## 改哪里

K 用 `--top_k` 改，不用改代码。

换一种比较方式或加一步重排序，改 `FaissStore.search`。现在这个函数编码查询、调用 `index.search`、再按行号取原文。

换向量模型时，先用新模型重新跑 `scripts/build_index.py`。查询和索引必须是同一个模型编出来的，否则内积没有意义。`run_baseline.py` 的 `--embed_model` 默认读索引 `meta.json` 里记下的那个目录。
